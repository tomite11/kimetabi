# ドメイン状態遷移・不変条件

この文書は `M0-A1` の成果物であり、旅行、枠、候補、支出、精算について、
実装とテストが守る状態遷移と業務不変条件をまとめる。プロダクト仕様の正本は
`doc/SPEC.md` であり、矛盾がある場合は同仕様書を優先する。

`MUST` は常に満たす条件、`MUST NOT` は禁止事項、`SHOULD` は合理的な理由が
なければ守る条件を表す。ここではMVPを国内旅行・日本円に限定する。

## 共通不変条件

- 旅行配下のリソースを参照または更新するときは、URLの `tripId` だけでなく、
  対象リソースの `trip_id` が同じ旅行であることを検証しなければならない。
- 旅行内の業務更新は、対象リソースの `version` を検証する。古いversionによる
  更新は最終書き込み勝ちにせず、現在値を伴う `409 Conflict` とする。
- 業務データ更新、対象リソースのversion更新、`trip.revision` の加算、必要な
  監査記録、Outboxイベントは、適用対象である限り同一トランザクションに置く。
- 金額はMVPでは整数円かつ `JPY` とする。負担額と送金額は負数を許さない。
- 退出・削除済みメンバーを物理削除して、過去の投票、支出、負担、送金の参照を
  壊してはならない。

## 旅行とメンバー

### 旅行フェーズ

自動フェーズは旅行のIANAタイムゾーンにおける日付で判定する。端末やサーバーの
ローカルタイムゾーンを使ってはならない。

| 現在日 | 自動フェーズ |
|---|---|
| `starts_on` より前 | `PLANNING` |
| `starts_on` 以上かつ `ends_on` 以下 | `TRAVELING` |
| `ends_on` より後 | `SETTLING` |

`phase_override` が設定されている場合は自動フェーズより優先する。上書きは表示と
主導線のフェーズを変えるが、支出、候補、精算などの業務データを暗黙に変更しない。
`ends_on` は `starts_on` 以降、`expected_member_count` は1以上でなければならない。

### メンバー状態

```text
（未参加） --参加--> ACTIVE --退出--> LEFT
                         `--削除--> REMOVED
LEFT / REMOVED --OWNERによる復旧--> ACTIVE
```

- 旅行ごとにACTIVEなOWNERが必ずちょうど1人存在しなければならない。
- OWNERは、別のACTIVEメンバーへのOWNER移譲と同一の業務操作を完了する前に、
  退出または削除されてはならない。
- OWNER移譲は、移譲先をOWNER、移譲元をORGANIZER以下へ変更してもACTIVEな
  OWNERが常に1人となるよう原子的に行う。
- 未精算残高があるメンバーは精算完了まで削除できない。
- 同じ旅行で同じFirebase UIDが再参加した場合、新規メンバーを作らず既存の
  メンバーを復帰させる。同名の別メンバーは許可する。
- MEMBERは自分が作成したDRAFTだけを編集・削除できる。確定支出の訂正は
  OWNERまたはORGANIZERだけが行い、変更履歴を残す。

## 枠、候補、投票、採択

### 枠状態

```text
OPEN --仮選択--> TENTATIVE --採択--> DECIDED
  |                    |                 |
  |                    `--解除----------> OPEN
  |                                      |
  +--現地決定--> DECIDE_LOCALLY          `--採択変更--> DECIDED
  `--対象外----> SKIPPED
```

`DECIDE_LOCALLY` はMVP後の状態であり、MVPでは新規遷移先として提供しない。
枠の追加、削除、並べ替え、分割では旅行日程内の日番号と一意な並び順を維持する。
初期枠は宿・往路・復路を旅行作成と同一トランザクションで生成する。

採択では次をすべて満たさなければならない。

- OWNERまたはORGANIZERだけが実行できる。
- 採択対象candidate、対象slot、URLのtripが同じ旅行に属する。
- `slot.adopted_candidate_id` の更新と `plan_item` の作成または更新を同一
  トランザクションで行い、成功時にslotは `DECIDED` となる。
- 採択変更時もslotとplan itemを矛盾させない。
- 採択由来のplan itemにCONFIRMED支出が紐づく場合、採択の解除または別候補への
  変更を拒否する。

### 候補とメタデータ

候補の採択状態の正本はcandidateではなく `slot.adopted_candidate_id` とする。
候補の業務状態 `OPEN` / `REJECTED` と採択状態を重複管理しない。

```text
OPEN --却下--> REJECTED --再検討--> OPEN
```

REJECTEDの候補は採択できない。すでに採択されている候補をREJECTEDにする操作は、
先に同一操作内で採択を解除できる場合に限る。

```text
PENDING --処理開始--> PROCESSING --成功--> COMPLETED
   ^                       |
   |                       +--一時障害--> FAILED_RETRYABLE --再取得--> PENDING
   |                       `--恒久障害--> FAILED_PERMANENT
   `---------------------------明示的な再取得-------------------------'
```

- URL候補は外部取得を待たず即時に作成し、外部取得失敗によって削除しない。
- 遅延したメタデータは、作成後にユーザーが編集した値を上書きしてはならない。
- 同じ冪等キーの再送で候補を二重作成してはならない。
- 概算の1人あたり額はACTIVEメンバー数ではなく
  `expected_member_count` を使う。
- `PER_PERSON` は単価に人数とunitsを反映し、`TOTAL` は総額を人数で割る。
  同じ入力に対する円単位の結果は決定的でなければならない。

### 投票

- 投票値は `YES` / `ANY` / `NO` のいずれかとする。
- `NO` には理由が必須で、その他の値では理由を必須にしない。
- 1候補・1メンバーにつき現在の投票は1件とし、再投票はその投票を更新する。
- ACTIVEメンバーだけが同じ旅行の候補へ投票できる。
- `NAMED` では投票者、選択、理由をACTIVEメンバーへ返す。`ANONYMOUS` では
  OWNER/ORGANIZERを含め、他者の投票者ID、選択、理由を返さず、集計、自分の
  投票、自分が未投票かだけを返す。

## 支出と按分

### 支出状態

```text
（未作成） --写真または金額--> DRAFT --確定--> CONFIRMED
                                      `--入力不備--> DRAFT
```

CONFIRMEDからDRAFTへの逆遷移は許可しない。確定後の訂正はversionを持つ更新として
扱い、変更前後、操作者、時刻を監査履歴へ残す。

| 条件 | DRAFT | CONFIRMED |
|---|---:|---:|
| 作成者 | 必須 | 必須 |
| 写真だけ | 許可 | 不可 |
| payer | 任意 | 同じ旅行のメンバーが必須 |
| amount / base amount | 任意 | 正の整数円が必須 |
| currency | 任意 | `JPY` が必須 |
| paid time | 任意 | 必須 |
| allocation type | 任意 | 必須 |
| expense share | 任意 | 1件以上必須 |

- 写真も金額もないDRAFTは作成しない。
- 同じ冪等キーによるDRAFT作成を繰り返しても、支出は1件だけとする。
- DRAFTからCONFIRMEDへの遷移と全按分条件の検証は同一トランザクションで行う。
- 全shareのメンバーは支出と同じ旅行に属し、重複してはならない。
- CONFIRMED時の最終的な整数円の負担額をメンバーごとに保存し、後から同じ
  入力や丸め方式に依存せず精算を再現できるようにする。

### 按分

- `EQUAL`: 全対象者のweightを1、fixed amountを未設定とする。
- `WEIGHT`: 全対象者のweightを正数、fixed amountを未設定とする。
- `FIXED_AND_WEIGHT`: 固定額指定者には0以上のfixed amount、残額配賦対象者には
  正のweightを設定できる。
- 対象者0人、負数、weight合計0、固定額合計が支出額を超える入力を拒否する。
- 固定額を差し引いた残額はweight比で高精度計算し、1円未満を切り捨てる。
  残余円は小数部の大きい順、同率ならmember ID昇順で1円ずつ配る。
- 同じ入力の負担額は常に同じで、最終負担額の合計は支出のbase amountと
  厳密に一致しなければならない。

## 精算

### 精算状態

```text
（未作成） --計算--> DRAFT --確定--> CONFIRMED --全送金受取確認--> COMPLETED
                         |
                         `--新精算の確定--> SUPERSEDED
CONFIRMED --新精算の確定--> SUPERSEDED
```

新しい精算を確定したときだけ、未完了の旧DRAFTまたはCONFIRMEDをSUPERSEDEDに
する。COMPLETEDをSUPERSEDEDへ変更しない。

- DRAFT精算は、その計算に使用したCONFIRMED支出と各支出versionを固定する。
- 精算確定後は対象支出、負担額、transferを変更しない。
- 精算確定後の支出追加・訂正は既存精算を変更せず、未反映変更として検出し、
  新しいDRAFTを計算する。
- メンバーごとの残高は「立替額－確定負担額」で計算し、全残高の合計は0とする。
- transfer総額は債務残高総額と一致し、残高が0でないメンバー数を `n` とすると
  貪欲法が生成するtransferは `max(0, n - 1)` 件以内とする。
- transferは正額で、送金元と送金先を同一メンバーにしない。
- 送金元本人だけが `PENDING` から `PAID`、送金先本人だけが `PAID` から
  `CONFIRMED` へ変更できる。管理者による代理操作は監査履歴を必須とする。
- 支払済みtransferは履歴上の事実として保持し、再精算の残高へ織り込む。

## M0の後続設計へ渡す事項

M0-A2では、本書の不変条件を外部キー、CHECK制約、一意制約、索引、確定負担額、
精算対象支出version、監査履歴へ落とす。M0-A3では、状態変更要求、version、
`409 Conflict` の現在値、冪等キーをOpenAPIへ落とす。

M0-A2/A3で確定した確定負担額、精算スナップショット、監査、投票公開設定、
DRAFT画像アップロードの判断は `doc/SPEC.md` 5.7、11.1を参照する。
Share TargetをMVPのリリース条件に含めるかは、引き続きM0全体の合流前に
解消する。
